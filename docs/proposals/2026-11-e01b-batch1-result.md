## 0. 結論

**產品：六次都滿分；C 對 B 是「量測無效」，B 對 A 是「天花板」。**
- 六次 run 的 Oracle 分項全部通過（13/13）。
- 依設計 §5.2 的判定順序：

| 比較 | 判讀 | 原因 |
|---|---|---|
| C 對 B | 第 1 條「量測無效」 | C2 不可嚴格比較（§2.1），C 組只剩 C1 一次可比；而且 C1、C2 的治理閉環都未完成，依設計 §3.4 不算「Full Governance 有參與執行」的樣本 |
| B 對 A | 第 2 條「天花板」 | 四次都可比，全部 13/13 |

- 參考（不是正式判讀）：把 C2 算進去，C 對 B 的產品分數也會停在「天花板」；但 C 組仍不能當成「完整治理全部啟用並完成」的證據。這一批無法判斷任何一組在產品上較好或較差。

**成本：C 較高，但只能當原始觀察；B 略高於 A。**
- **原始觀察（六次全部）：**
  - C1、C2 的牆鐘時間、總輸入 Token、未快取輸入 Token、輸出 Token，都高於其他四次。
  - B 組兩次在同樣四項上都略高於 A 組兩次。
- **可比較的子集（不含 C2）：**
  - C1 在上述四項仍都高於 A、B 組的任何一次。
  - 但 C 只剩一次可比，無法得出可靠的 C−B 組間成本估計。
- **時間要打折扣：** 執行順序不平衡（§2），C 多出來的時間主要在模型端，而且 C 兩次都遇到模型資訊逾時（§5）。Token 是比較可靠的成本證據。
- C 組沒有結案，結案本身的成本這批沒有量到。若以完整治理（含結案）來看，C 的成本是低估。
- 依設計 §5.2，成本只記差額、不設門檻，所以這裡不做方向判定。

**治理閉環：C 組未完成（設計 §3.4）。**
- SessionStart 已確認，建立了 session 身分；Stop 有間接觸發跡象，執行是否正常結束未驗證（§4.1）。
- 兩次都**沒有產生 closeout**，R2 也沒有 `RELEASED`。
- 依設計 §3.4，C 組記為「產品結果有效、治理閉環未完成」兩欄，不能當作「Full Governance 整套（含結案）有參與執行」的樣本。

**能寫的結論：**
- 在這個任務、這個模型上，「Core Rules＋完整治理文件＋hooks＋canonical memory（未含有效結案）」相對 Rules Only，沒有觀察到額外的產品價值，成本較高。C 對 B 的正式判讀是「量測無效」，所以這只是原始觀察。
- Rules Only 相對 Baseline 也沒有觀察到產品差異（天花板），成本略高。

**這只是 n=2、撞到天花板的探索性觀察。**
- 不能推論到較難的任務。
- 不能歸因到單一元件。
- 不計入正式 E-01B 樣本。
- 沒有測到持續執行、可靠記憶、跨 session 接續與減少 Owner 介入。

## 1. 任務與設定

### 1.1 任務

- **原本抽中的題目取消資格。** 開跑前的獨立審查發現，設計 §1.3 抽中的題目已經在先前的 Gate3 實驗 clone 中被 agent 實作過，違反「沒有被既有 Agent 修過」的入選條件。Owner 裁定換題，該題的 Oracle 不挽救。
- **新題目由 Owner 直接指定，沒有抽籤**（與設計 §1.3 不同）。題目是同一個 Internal Consumer 中、依公開標準規格某一節實作的離線 descriptor 內容解讀，只用合成資料，不碰硬體。
- **資格確認：** 唯讀檢查了該 Consumer 的所有本機副本、所有 repo 分支、遠端、三種 agent 的本機紀錄，以及既有的實驗目錄，都沒有這項解讀的實作。
- **代表性限制：** 該 Consumer 的真實擷取檔裡沒有這種請求，所以這項功能的實際需求偏弱。

### 1.2 組別與起點

- **起點：** 三組都從同一個 consumer commit 出發，再各自套上一個 overlay commit（A：移除治理面；B：只有 Core Rules；C：完整治理＋可攜形式的 Codex SessionStart／Stop hooks）。framework 版本是 `db2a2003`。
- **事前核對：**
  - 三組被解讀的產品原始檔逐位元組相同，都沒有這項解讀。
  - B、C 兩組的 Core Rules 區塊逐位元組相同。
  - C 組看得到的 memory 裡沒有本題的答案。
  - 起點、overlay 雜湊與任務規格都在製作 Oracle 之前固定。
- **任務規格：** 三組收到逐字相同的 prompt（stdin），內容包括設計 §2.1 的共同安全底線。

### 1.3 執行

- 每次 run 是一個 `codex exec --json` 回合，Codex CLI 0.169，三組使用相同的模型與 reasoning 設定。
- 指定的權限與設定也相同：`workspace-write` 沙箱（Windows elevated），approval `never`，關閉 MCP、multi-agent 與 Codex memories。但 C2 實際生效的設定和其他五次不同，見 §2.1。
- 每次 run 都有獨立的 clone、`CODEX_HOME`、TMP；單次上限 60 分鐘。
- 六次全部在事前核准的成本上限內（設計 §6），沒有作廢、沒有被強制終止。

### 2.1 C2 的實際設定（2026-11-15 補）

- C2 啟動時，Codex 更新可用模型資訊多次逾時。C1 有一次逾時，A、B 都沒有。
- C2 因此用了另一套備用設定，和其他五次不同：
  - context window 較小；
  - 基礎指令與工具定義不同，一個存取方案欄位是空值；
  - 多一則 developer 訊息，skills 清單較短。
- 相同的部分：模型名稱、reasoning、approval、沙箱權限、prompt 與 `AGENTS.md`。六次都沒有發生 context 壓縮。
- 原結果寫「權限與設定也相同」，沒有揭露這一點，由獨立 review（#305 B-1）指出。
- **Owner 2026-11-15 裁定：C2 不可嚴格比較。** 標準和第二批的 B1 一致（第二批結果，Draft PR #306）。這不影響 C2 的 Oracle 分數。

## 4. 各組的實際行為

### 4.1 C 組（Full Governance）：兩欄記錄（設計 §3.4）

| | C1 | C2 |
|---|---|---|
| 產品結果 | 有效，13/13 | 有效，13/13 |
| 執行設定 | 可比較 | **不可嚴格比較**（§2.1） |
| 開跑前 trusted_hash | 有 | 有 |
| SessionStart（session 身分紀錄） | 已確認 | 已確認 |
| Stop | 有間接觸發跡象；執行是否正常結束未驗證 | 同左 |
| closeout `valid` | **無**（沒有產生 closeout） | **無** |
| R2 `RELEASED` | **無** | **無** |
| canonical memory 寫入 | 有（`memory_record`，有警告） | 有（`memory_record`，有警告） |
| 治理閉環 | **未完成** | **未完成** |

**Stop 的證據強度：**
- 證據只有鎖定檔的時間落在回合結束那一秒。
- 沒有確認這個鎖定檔只可能由 Stop 建立，也沒有 hook 的執行結果（`codex exec --json` 不輸出 hook 事件，Codex 的本機紀錄也是空的）。
- 所以只能說 Stop 有觸發跡象，不能證明它正常完成。

**為什麼沒有 closeout（Owner review 2026-11-15 的判讀見本小節最後）：**
- 三組的 prompt 逐字相同，沒有要求結案；這是共同底線設計的結果。
- agent 依框架的結案規則，沒有自行準備結案資料。
- Stop 有間接觸發跡象（只留下鎖定檔），沒有任何結案紀錄。

這屬於「hook 有觸發但結案沒有完成」：依 Owner 先前的原則，這是要留在報告裡的治理負面證據，不是準備問題。
- 單回合 `codex exec`、prompt 沒有要求結案時，本來就不會觸發有效的結案與 R2 流程。
- 這比較像這個實驗沒有覆蓋完整結案流程；不能單憑缺少 closeout，就認定 framework 有新的 bug（Owner review 2026-11-15）。

**其他觀察：**
- C 組兩次都呼叫了 canonical writer 與 memory 檢查工具。guard 沒有阻擋，但有警告（找不到 canonical writer 與 memory authority guard、缺少 canonical memory、memory 未綁定）。
- 為了讓 memory 檢查工具跑得動，C1 用環境變數設了只在該程序有效的 git `safe.directory`，繞過 git 的擁有者檢查。
- 為了弄清楚用法，agent 去讀了框架工具的原始碼。
- C 組把測試輸出存進 memory 目錄。
- C 組新增的測試案例數是三組中最少的。但這是參數化後的案例數，不是測試強度：獨立 review 事後在每次新增的程式上放 11 種小錯，六次的測試都全部抓到（#305 §2 第 20 項）。所以沒有證據顯示 C 的測試比較弱或比較強。

### 4.2 B 組（Rules Only）

- 依 Core Rules 自行手寫了 PLAN.md 與幾個 memory 檔，沒有使用 framework 工具。
- 這和設計 §2.2 對 B 組的定義不一致（B 組不帶 Governance Memory、不寫 canonical memory）。原因是 B 組的 Core Rules 本身有「必須記錄事件」的要求。
- 依設計 §2.2，這些不算 B 組的治理產出；但 B 比 A 多的成本，有一部分是手寫紀錄。

### 4.3 A 組（Baseline）

- 沒有寫任何紀錄檔，只做產品修改與測試。

## 5. 限制

- **樣本與天花板：** 每組 2 次，而且全部滿分。題目對這個模型太簡單，分辨力不足。
- **歸因：** B 與 C 之間同時差了規則、hooks、memory 幾項，加上 C 的結案沒有發生，結論只能到「這個整套組合」，不能歸因到單一元件。
- **隔離（Owner 選擇輕量做法，否決專用帳號、容器與加密封存，認為是過度治理）：**
  - 每次 run 結束後，整個 run 資料夾就歸檔到沙箱帳號讀不到的位置，原處刪除。後面的 run 讀不到前面的解答。
  - 沙箱帳號讀得到、但沒有阻擋的位置：協調 session 的對話紀錄（含 Oracle 內容）與其他本機資料。事後掃描六次 rollout，都沒有提到這些位置；這是事後偵測，不是事前阻擋。
  - 三組都載入了 Owner 相同的全域 Codex skills。
- **Oracle：** 由協調 session 撰寫，不是獨立 reviewer；封存值與 manifest 同處（§2）。
- **執行順序與時間：** 不平衡（§2），C 永遠最後。C 多出來的時間主要在模型端，不在指令執行；模型端時間受 API 狀況影響，而 C 兩次都遇到模型資訊逾時。時間差混有順序與網路因素。
- **C2 的設定：** 不可嚴格比較（§2.1）。C 組只剩 C1 一次可比。
- **共同底線：** 三組都從 prompt 收到安全底線，所以量不到「底線由治理面提供」的價值（沿用設計 §2.1 的限制）。
- **意外事件：** 第一次 run 的歸檔途中中斷，原處已被部分刪除，之後補齊歸檔。事後核對：歸檔的 HEAD 和 git 狀態與 agent 的修改一致。

## 6. 一次性準備成本（定性，不算進任何一組）

- **隔離方案：** 前後提出兩次較重的隔離方案，都被 Owner 以「準備成本高於實驗價值」否決，最後只沿用既有的拒絕讀取設定與歸檔。
- **C 組 hook 信任：**
  - Owner 手動信任一次，因為 CLI 參數問題失敗。
  - 協調 session 代寫信任時被工具的安全檢查擋下，後來在 Owner 明確要求後才寫入。
  - 為了確認 hook 是否真的執行，額外做了幾次測試，也讀了 Codex 原始碼。原因是 `--json` 輸出不顯示 hook 事件，hook 產物又在 gitignore 的目錄裡。
