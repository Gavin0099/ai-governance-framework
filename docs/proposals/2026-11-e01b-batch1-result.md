## 0. 結論

**產品：六次都滿分，兩組比較都是「天花板」。**
- 六次 run 的 Oracle 分項全部通過（13/13）。
- 依設計 §5.2 的判定順序，C 對 B、B 對 A 都在第 2 條「天花板」停下。這一批無法判斷任何一組在產品上較好或較差。

**成本：C 明顯最高，B 略高於 A。**
- C 組兩次的牆鐘時間、總輸入 Token、未快取輸入 Token、輸出 Token，都高於 A、B 組的任何一次。
- 總輸入 Token 的差距最大，遠大於組內兩次之間的差異。
- B 組兩次在同樣四項上都略高於 A 組兩次。總輸入 Token 的差距很小，接近組內差異。
- 依設計 §5.2，成本只記差額、不設門檻，所以這裡不做方向判定。

**治理閉環：C 組未完成（設計 §3.4）。**
- C 組的 hook 都實際觸發了：SessionStart 建立了 session 身分，Stop 在每個回合結束時都有執行。
- 但兩次都**沒有產生 closeout**，R2 也沒有 `RELEASED`。
- 依設計 §3.4，C 組記為「產品結果有效、治理閉環未完成」兩欄，不能當作「Full Governance 整套（含結案）有參與執行」的樣本。

**能寫的結論：**
- 在這個任務、這個模型上，「Core Rules＋完整治理文件＋hooks＋canonical memory（未含有效結案）」相對 Rules Only，沒有觀察到額外的產品價值，成本明顯較高。
- Rules Only 相對 Baseline 也沒有觀察到產品差異，成本略高。

**這只是 n=2、撞到天花板的探索性觀察。**
- 不能推論到較難的任務。
- 不能歸因到單一元件。
- 不計入正式 E-01B 樣本。

## 1. 任務與設定

### 1.1 任務

- **原本抽中的題目取消資格。** 開跑前的獨立審查發現，設計 §1.3 抽中的題目已經在先前的 Gate3 實驗 clone 中被 agent 實作過，違反「沒有被既有 Agent 修過」的入選條件。Owner 裁定換題，該題的 Oracle 不挽救。
- **新題目由 Owner 直接指定，沒有抽籤**（與設計 §1.3 不同）。題目是同一個 Internal Consumer 中、依公開標準規格某一節實作的離線 descriptor 內容解讀，只用合成資料，不碰硬體。
- **資格確認：** 唯讀檢查了該 Consumer 的所有本機副本、所有 repo 分支、遠端、三種 agent 的本機紀錄，以及既有的實驗目錄，都沒有這項解讀的實作。
- **代表性限制：** 該 Consumer 的真實擷取檔裡沒有這種請求，所以這項功能的實際需求偏弱。

### 1.2 組別與起點

- **起點：** 三組都從同一個 consumer commit 出發，再各自套上一個 overlay commit（A：移除治理面；B：只有 Core Rules；C：完整治理＋可攜形式的 Codex SessionStart／Stop hooks）。framework 版本是 `db2a2003`。
- **事前核對：**
  - 三組被解讀的產品原始檔逐位元組相同，都沒有這項解讀。
  - B、C 兩組的 Core Rules 區塊逐位元組相同。
  - C 組看得到的 memory 裡沒有本題的答案。
  - 起點、overlay 雜湊與任務規格都在製作 Oracle 之前固定。
- **任務規格：** 三組收到逐字相同的 prompt（stdin），內容包括設計 §2.1 的共同安全底線。

### 1.3 執行

- 每次 run 是一個 `codex exec --json` 回合，Codex CLI 0.169，三組使用相同的模型與 reasoning 設定。
- 權限與設定也相同：`workspace-write` 沙箱（Windows elevated），approval `never`，關閉 MCP、multi-agent 與 Codex memories。
- 每次 run 都有獨立的 clone、`CODEX_HOME`、TMP；單次上限 60 分鐘。
- 六次全部在事前核准的成本上限內（設計 §6），沒有作廢、沒有被強制終止。

## 2. 與設計 v5 的差異（揭露）

| 設計 | 實際 | 影響 |
|---|---|---|
| 設計 §1.3 事前記錄的隨機抽題 | 原題取消資格後，由 Owner 直接指定 | 沒有抽籤；題目不是為了預期 A／B 失敗而選的 |
| 設計 §3.3 範本與登入檔由 Owner 複製 | 由協調 session 複製（Owner 在對話中要求代做） | agent 不經手；Owner 沒有逐次操作 |
| 設計 §3.4 C 組開跑前需有 trusted_hash | 協調 session 寫入 Owner 先前對逐位元組相同的 hook 給過的 trusted_hash，再用 Codex app-server `hooks/list` 確認狀態為 trusted | 開跑前條件成立；hook 實際觸發見 §4 |
| 設計 §3.5 平衡的組別順序 | A1→B1→A2→B2→C1→C2（C 組因 hook 信任較晚準備，排在最後） | 時段與服務端負載可能與組別混淆，成本比較要打折扣 |
| 設計 §2.3 remote 指向無憑證的 bare repo | remote 指向本機的非 bare 準備 repo | 事後確認：六次都沒有新 commit，準備 repo 的分支 ref 沒有變動 |
| 設計 §4.1 Oracle 由不參與執行的規劃 session 撰寫 | 由協調 session 撰寫（不參與執行） | 符合；但不是獨立 reviewer，見 §5 |
| 設計 §4.4 Owner 在執行前獨立保存 SHA-256 | 封存值只存在 Oracle 目錄內，與 manifest 同處；檔案時間在第一次 run 之前 | 和上一次離線 Oracle 的限制相同：雜湊本身不能證明測前未改 |
| 設計 §4.5 Oracle 列入 deny 範圍 | Oracle 放在 Codex 沙箱帳號被拒絕讀取的目錄，實測讀不到 | 其他讀得到的位置見 §5 |
| — | 執行腳本沒有正確記錄 `codex exec` 的結束碼（記成 null） | 完成與否改由 rollout 的最後訊息與評分判定 |
| — | 評分加了一條規則：新的失敗測試要單獨重跑兩次，都通過才記為不穩定；這條規則在封存前加入 | 有一次 run 用到這條規則（一個網路測試偶發連線中斷） |

- **Oracle 的 13 個分項：**

  - 1 個確認其他既有解讀不受影響。

- **六次的共同點：**
  - 都沒有 commit 或 push，沒有改允許範圍外的檔案，沒有動 fixture 或 evidence，沒有使用子 agent。

## 4. 各組的實際行為

### 4.1 C 組（Full Governance）：兩欄記錄（設計 §3.4）

| | C1 | C2 |
|---|---|---|
| 產品結果 | 有效，13/13 | 有效，13/13 |
| 開跑前 trusted_hash | 有 | 有 |
| SessionStart 實際觸發（session 身分紀錄） | 有 | 有 |
| Stop 實際觸發 | 有（每回合） | 有（每回合） |
| closeout `valid` | **無**（沒有產生 closeout） | **無** |
| R2 `RELEASED` | **無** | **無** |
| canonical memory 寫入 | 有（`memory_record`） | 有（`memory_record`） |
| 治理閉環 | **未完成** | **未完成** |

**為什麼沒有 closeout（初步判讀，待 review）：**
- 三組的 prompt 逐字相同，沒有要求結案；這是共同底線設計的結果。
- agent 依框架的結案規則，沒有自行準備結案資料。
- Stop hook 有執行，但只留下鎖定檔，沒有任何結案紀錄。

這屬於「hook 有觸發但結案沒有完成」：依 Owner 先前的原則，這是要留在報告裡的治理負面證據，不是準備問題。它同時暴露一個設計缺口：在單回合 `codex exec`、prompt 沒有要求結案時，Full Governance 的結案環節不會發生。

**其他觀察：**
- C 組兩次都呼叫了 canonical writer 與 memory 檢查工具。guard 沒有阻擋，但有警告。
- 為了弄清楚用法，agent 去讀了框架工具的原始碼。
- C 組把測試輸出存進 memory 目錄。
- C 組新增的測試數是三組中最少的。驗收只要求「有新增且通過」，所以不扣分；但多出的成本沒有換到更多測試。

### 4.2 B 組（Rules Only）

- 依 Core Rules 自行手寫了 PLAN.md 與幾個 memory 檔，沒有使用 framework 工具。
- 依設計 §2.2，這些不算 B 組的治理產出。

### 4.3 A 組（Baseline）

- 沒有寫任何紀錄檔，只做產品修改與測試。

## 5. 限制

- **樣本與天花板：** 每組 2 次，而且全部滿分。題目對這個模型太簡單，分辨力不足。
- **歸因：** B 與 C 之間同時差了規則、hooks、memory 幾項，加上 C 的結案沒有發生，結論只能到「這個整套組合」，不能歸因到單一元件。
- **隔離（Owner 選擇輕量做法，否決專用帳號、容器與加密封存，認為是過度治理）：**
  - 每次 run 結束後，整個 run 資料夾就歸檔到沙箱帳號讀不到的位置，原處刪除。後面的 run 讀不到前面的解答。
  - 沙箱帳號讀得到、但沒有阻擋的位置：協調 session 的對話紀錄（含 Oracle 內容）與其他本機資料。事後掃描六次 rollout，都沒有提到這些位置；這是事後偵測，不是事前阻擋。
  - 三組都載入了 Owner 相同的全域 Codex skills。
- **Oracle：** 由協調 session 撰寫，不是獨立 reviewer；封存值與 manifest 同處（§2）。
- **執行順序：** 不平衡（§2），C 組成本可能受時段影響。
- **共同底線：** 三組都從 prompt 收到安全底線，所以量不到「底線由治理面提供」的價值（沿用設計 §2.1 的限制）。
- **意外事件：** 第一次 run 的歸檔途中中斷，原處已被部分刪除，之後補齊歸檔。事後核對：歸檔的 HEAD 和 git 狀態與 agent 的修改一致。

## 6. 一次性準備成本（定性，不算進任何一組）

- **隔離方案：** 前後提出兩次較重的隔離方案，都被 Owner 以「準備成本高於實驗價值」否決，最後只沿用既有的拒絕讀取設定與歸檔。
- **C 組 hook 信任：**
  - Owner 手動信任一次，因為 CLI 參數問題失敗。
  - 協調 session 代寫信任時被工具的安全檢查擋下，後來在 Owner 明確要求後才寫入。
  - 為了確認 hook 是否真的執行，額外做了幾次測試，也讀了 Codex 原始碼。原因是 `--json` 輸出不顯示 hook 事件，hook 產物又在 gitignore 的目錄裡。
- **與治理無關的執行問題：** 歸檔工具遇到沙箱帳號建立、外部帳號讀不到的暫存資料夾，修正腳本後續跑。

## 8. 想請 reviewer 特別檢查的地方

1. §0 的判定是否照設計 §5.2 的順序。特別是：產品判在「天花板」，而成本不做方向判定。
2. C 組依設計 §3.4 記為「治理閉環未完成」是否正確。結論的措辭（「未含有效結案」）有沒有過度或不足。
3. §2 的偏離是否足以讓本批判為「量測無效」（設計 §5.2 第 1 條）。例如：Oracle 封存沒有獨立保存、順序不平衡、沙箱讀得到協調 session 的紀錄。
4. 「單回合 exec 且 prompt 沒要求結案時，結案不會發生」應該記為 framework 的缺口，還是實驗設計的缺口，或兩者都是。
