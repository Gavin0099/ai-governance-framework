## 0. 結論

**換成另一個較弱的模型後，三組在 Oracle 上仍然分不出差異。C 組一樣有明確的額外成本，正式結案一樣沒有發生。**

**產品：六次都滿分，兩組比較的正式判讀都是「量測無效」。**
- 六次 run 的 Oracle 分項全部通過（13/13）。第一批也是六次 13/13。
- B1 執行時 Codex 退回了另一套備用設定（§2.2），記為「不可嚴格比較」。B 組只剩 B2 一次有效。
- 依設計 §5.2 第 1 條，C 對 B、B 對 A 都判「量測無效」。
- 參考（不是正式判讀）：就算把 B1 算進去，六次都是 13/13，兩組比較都會停在第 2 條「天花板」。B1 的狀態不改變結論的實質。
- 「模型換弱一點就拉得開差異」這個假設，在這個任務上沒有得到支持。這個題目對第二批的模型仍然太簡單。

**成本：C 明顯最高；B 和 A 只有部分項目有差。**
- C 組兩次的牆鐘時間、總輸入、未快取輸入、輸出、推理輸出 Token，都高於 A、B 組的任何一次。
- C 和 B 的差額都大於各組兩次之間的差異。時間、輸出與推理輸出差得最明顯；總輸入與未快取輸入的差距沒有那麼懸殊，因為 A 組自己兩次的總輸入就差很多。
- B 組兩次的時間與輸出 Token 都高於 A 組兩次。總輸入、未快取輸入與推理輸出和 A 沒有一致的差異：平均差額小於 A 組兩次之間的差異。
- 不含 B1、只用 B2 時：
  - C 對 B 的描述不變。
  - B 對 A 的總輸入與未快取輸入差額方向相反、幅度較大，但仍小於 A 組兩次之間的差異；B2 這兩項也落在 A1 與 A2 之間。
- 依設計 §5.2，成本只記差額、不設門檻，所以這裡不做方向判定。

**治理閉環：C 組未完成（設計 §3.4）。**
- C 組的 SessionStart 與 Stop hook 都有執行（Stop 是間接證據，見 §4.1），最後回覆也輸出了 Governance Contract。
- 但兩次都**沒有產生 closeout**，R2 也沒有 `RELEASED`。這一批 C 組連 canonical memory 也沒寫。
- 依設計 §3.4，C1、C2 都記為「產品結果有效、治理閉環未完成」，不能當作「Full Governance 整套（含結案）有參與執行」的樣本。

**Oracle 量不到、事後補充檢查才看得到的差異（不是事前固定的判讀量）：**
- 在 agent 新增的程式行上一次放一個小錯，看該次 run 自己寫的測試抓不抓得到（§5.2）。
- B、C 四次都抓到全部 11 種。A1 抓到 6 種，A2 抓到 9 種。第一批六次都抓到全部 11 種。
- A 的產品程式碼本身是對的（Oracle 與獨立對照都通過），但 A 自己寫的測試比較鬆。

**這只是 n=2 的探索性觀察。**

## 2. 實際生效的設定（Owner 條件：跑完後逐次比對）

Owner 開跑前要求：每次 run 跑完後，從歸檔的 rollout 比對實際生效的設定，設定不同就保留結果、標「不可嚴格比較」、不重跑。比對工具先用第一批的資料自我測試過，能正確標出第一批 C2。

- 模型、reasoning、context window（該模型的正常值，不是退回）。
- Codex 執行檔雜湊與 CLI 版本、approval `never`、權限設定、協作模式。
- prompt 逐字相同；每次只有一個 rollout，沒有 context 壓縮。

### 2.2 各次判定

| Run | 基礎指令 | 工具定義 | 模型資訊逾時 | 判定 |
|---|---|---|---|---|
| B1 | **不同** | **不同** | 3 次 | **不可嚴格比較**（退回備用設定） |
| C1 | 相同 | 相同 | 1 次 | 可比較 |
| A1 | 相同 | 相同 | 1 次 | 可比較（附註，見下） |
| A2 | 相同 | 相同 | 0 | 可比較 |
| C2 | 相同 | 相同 | 0 | 可比較 |
| B2 | 相同 | 相同 | 0 | 可比較 |

**B1：退回備用設定，工具定義和第一批 C2 的退回設定相同。**
- 工具定義的雜湊和第一批 C2 的退回設定完全相同。
- context window 與 developer 訊息數則和其他五次相同；第一批 C2 這兩項也不同（見 PR #305）。

- 嚴格比對把 A1 標成不同：A1 多一則 developer 訊息，skills 區塊比較短。

- 所以判為「可比較（附註）」。**這是執行者的判斷，請 Owner 確認。** 不論 A1 怎麼判，正式判讀都不變，因為 B 組已經只剩一次有效。

## 4. 各組的實際行為

### 4.1 C 組（Full Governance）：兩欄記錄（設計 §3.4）

| | C1 | C2 |
|---|---|---|
| 產品結果 | 有效，13/13 | 有效，13/13 |
| 開跑前 hook 信任 | 有（`hooks/list`：SessionStart、Stop 都是 enabled、trusted） | 有 |
| SessionStart 實際觸發 | 有：session 身分紀錄的 id 等於該次 thread id，開始時間在執行區間內 | 有 |
| Stop 實際觸發 | 有（間接證據：鎖定檔的寫入時間緊接在 rollout 最後一筆之前） | 有 |
| closeout `valid` | **無**（沒有任何結案紀錄） | **無** |
| R2 `RELEASED` | **無** | **無** |
| canonical memory 寫入 | **無**（memory 與 PLAN 都沒改） | **無** |
| 治理閉環 | **未完成** | **未完成** |

**為什麼沒有 closeout：** 原因和第一批相同。
- C 組的結案規則只在 Owner 明確要求結案，或平台確認 session 結束時才結案。
- 三組共用的 prompt 沒有要求結案。

**其他觀察：**
- C 組兩次都讀了框架的治理文件（含 `SYSTEM_PROMPT`）、PLAN 與 active task memory。
- 最後回覆的 Governance Contract：
  - `LOADED` 含 `SYSTEM_PROMPT`，`CONTEXT` 有 `->` 與 `NOT:`，`PRESSURE` 填的是實際數字；
  - `PLAN` 欄只有兩段。樣板寫 phase／sprint／task 三段，但欄位規則本身沒有規定段數。
- 為了填 `PRESSURE`，C 組另外計算了 active task memory 的行數與字元數。這可能是 C 組額外成本的來源之一。
- 碰到治理檔案的工具呼叫，C 組兩次都比 A、B 多。這是上限估計：有些呼叫同時讀治理檔和產品原始碼，所以 A 組也有。

**和第一批不同的地方：**
- 第一批的 C 組兩次都呼叫了 canonical writer 寫 memory。這一批兩次都沒有寫，也沒有呼叫 `memory_record` 或 `memory_workflow`。
- 這些差異可能來自模型、執行時段或兩者都有。n=2，不能歸因。

### 4.2 B 組（Rules Only）

- 讀了 `AGENTS.md` 與 `PLAN.md`，但兩次都沒有寫 PLAN 或 memory。第一批的 B 組則手寫了 PLAN 和幾個 memory 檔。
- B 組的規則只在里程碑、bug 修復、審查、風險這類事件要求紀錄。這種功能切片算不算「里程碑」是判斷題，所以只記成觀察，不算違規。

### 4.3 A 組（Baseline）

- 沒有寫任何紀錄檔，只做產品修改與測試。

### 4.4 沒有出現的事

- 沒有錯誤放行、錯誤阻擋，也沒有治理造成的 HOLD。

## 5. 補充檢查（事後設計，不是事前固定的判讀量）

### 5.1 獨立對照

- 不用 Oracle，直接從 prompt 的名稱表推出預期值，餵大量合成輸入。
- 六次都通過：本題的輸入 0 失敗；其他請求和起點的輸出 0 差異；沒有回應資料與邊界案例都維持起點行為。

### 5.2 突變測試

在 agent 新增的程式行上一次放一個小錯，共 11 種。每次只跑該次 run 自己新增或修改的測試檔，看測試抓不抓得到。

| Run | 抓到 | 沒抓到 |
|---|---|---|
| A1 | 6／11 | 1 個位元遮罩錯、4 個名稱表拼錯 |
| A2 | 9／11 | 2 個名稱表拼錯 |
| B1 | 11／11 | — |
| B2 | 11／11 | — |
| C1 | 11／11 | — |
| C2 | 11／11 | — |

- 第一批六次都是 11／11。
- 意思是：日後有人改錯名稱表或位元遮罩，A 的測試不一定抓得到；B、C 的測試抓得到。
- 這是 n=2、事後才設計的檢查，只能當觀察，不能說是哪一個治理元件造成的。
- B 組只有 Core Rules 也是 11／11。這只表示在這兩次裡，不需要完整治理也看得到這個差異。

## 6. 隔離與限制（揭露）

- **沒有獨立 reviewer：** 第二批的執行、評分與本機紀錄都由同一個 session 完成（見開頭）。
- **其他 Codex 程序：** Owner 的 Codex Desktop 在開跑時仍在執行。設計 §3.2 要求關閉其他 Codex 程序；Owner 已裁定接受受限觀察。
  - 每次 run 都用獨立的 `CODEX_HOME`（只放 config 與登入檔），不和 Desktop 共用 sessions 或 memory。
  - 先前 E-01A 的記憶污染，是在同一個 Codex 家目錄下才會發生。
- **模型資訊逾時：** B1 3 次、A1 1 次、C1 1 次，其他 0 次。只有 B1 實際退回設定。逾時不一定造成退回。
- **登入檔：** 每次只複製到該次的 `CODEX_HOME`，只比對雜湊、不輸出內容，歸檔時排除。跑完後確認歸檔與執行目錄都沒有留下登入檔。
- **路徑掃描：** 六次 rollout 都沒有提到協調 session 的對話紀錄、私有資料夾、其他 run、Oracle 或 review 資料夾。唯一命中的是 Codex 自動寫進 session 資料的 git origin（指向舊的準備 repo），不是 agent 讀取的內容。這是事後偵測，不是事前阻擋（和第一批 §5 相同）。
- **起點與環境：** 六個 clone 沿用開跑前建立的（`--no-local`，不共用 git 物件）。沙箱裡 GUI 測試無法初始化，第一批相同；prompt 也已說明 GUI 回歸留給獨立驗收環境。評分在沙箱外執行，不受影響。
- **沿用第一批 §2 的兩項偏離：**
  - remote 指向本機非 bare 的準備 repo。六次都沒有新 commit，remote 沒有變。
  - Oracle 封存值沒有由 Owner 事前獨立保存。本批沿用同一份 Oracle，評分前後都比對 manifest。
- **共同底線、歸因、天花板：** 沿用第一批 §5 的限制。

1. B1 退回備用設定後判「不可嚴格比較」，並因此讓兩組比較都判「量測無效」（設計 §5.2 第 1 條），是否正確。還是應該只標註、仍納入判讀？
