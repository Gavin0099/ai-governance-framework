## 1. Blocking

### B-1　C2 的執行環境和其他五次不同，結果沒有揭露

**事實（從六次的 Codex rollout 與 stderr 比對）：**
- C2 啟動時，「更新可用模型資訊」多次逾時。C1 有一次逾時，A、B 都沒有。
- 結果 C2 用了一組退回的執行設定，和其他五次不同：
  - 可用的 context window 較小；
  - 系統基礎指令（base instructions）的內容不同；
  - 提供給 agent 的工具清單、skills 清單不同，還多一則開發者訊息；
  - 一個存取分級欄位是空值（其他五次有值）。
- 相同的部分：模型名稱、reasoning effort、approval、沙箱權限設定、prompt、各組的 `AGENTS.md`。六次都沒有發生 context 壓縮。

**為什麼是 blocking：**
- 結果 §1.3 寫「權限與設定也相同」，和事實不符。
- 設計 §5.2 第 1 條：任一組有效 run 少於 2 次（例如不可比較）時，該比較判為「量測無效」。C2 是否可比，會影響 C 組比較的判讀類別。
- 只看設定一致的 C1，C 組成本仍然明顯高於 A、B，方向不變，但 C 組只剩 1 次。

**建議：**
- 在結果 §2 的差異表加一列，揭露 C2 的執行環境不同。
- C 組成本同時列「兩次」與「只看 C1」。
- 請 Owner 裁定 C2 是否可比；在裁定之前，不把 C 組兩次的平均當成乾淨的比較。

## 3. 非 blocking（依嚴重度）

### N-1　執行順序與時間

- 順序不平衡（C 最後）已在結果 §2 揭露。
- 補充：C 多出來的時間主要在模型端，指令執行時間沒有明顯差異。C 組兩次都遇到模型資訊抓取逾時。
- 時間差應註明混有順序與網路因素；Token 是較可靠的成本證據。

### N-2　執行期間有其他 Codex 活動

- 協調 session 在第一次 run 的最後一分多鐘，用 C1 預定的 `CODEX_HOME` 與 clone 做了 hook 測試；之後 C1 的 clone 與 home 已重建，C1 正式執行是乾淨的。
- Owner 的 Codex Desktop 在整批執行期間都開著。設計 §3.2 要求關閉其他 Codex 程序。
- 各 run 用獨立的 `CODEX_HOME`，沒有看到互相影響的跡象，但結果沒有揭露。

### N-3　收集腳本有三個欄位沒有量到東西

- 收集腳本找的事件名稱和這個 Codex 版本的 rollout 格式對不上，所以「人工介入」「最後回報」「hook 事件」三個欄位一定是 0 或空值。
- 我改用正確的事件另外確認：人工介入確實是 0，最後回報與 Oracle 一致（§2 第 15、16 項）。
- 數字沒錯，但依據不是收集腳本。下一批用之前要修。

### N-4　B 組的成本包含手寫紀錄

- 結果 §4.2 寫明 B 組的手寫紀錄不算 B 組的治理產出。
- 補充：Core Rules 本身要求「必須記錄的事件」要更新 memory 與 PLAN，所以 B 組相對 A 多出的成本，有一部分是手寫紀錄。這和設計 §2.2「B 組不寫 memory」的定義不同，解讀 B−A 成本差時要考慮。

### N-5　C 組治理工具的摩擦

- C1 為了讓 memory 檢查工具能執行，自己用環境變數設了只在該程序生效的 git `safe.directory`，用來繞過 git 的擁有者檢查。
- 工具回報的警告包括找不到 canonical writer、找不到 memory authority guard、缺少 canonical memory、memory 未綁定。
- Stop hook 的結束碼與輸出沒有任何紀錄（`--json` 不輸出 hook 事件，Codex 的 log 資料庫是空的）。「Stop 有執行」的證據只有鎖定檔的時間落在回合結束時。結果 §4.1 寫成「有（每回合）」，應註明證據強度。

### N-6　Oracle 與評分程式的潛在弱點（都沒有影響這六次）

§2 第 7 項的獨立檢查六次全部通過，所以以下只是下一批要修的地方：

- 名稱對照表只測到一部分項目。
- 「恰好一筆 descriptor」那一項只比對欄位名稱，沒有比對欄位值與位移。
- 數值比較排除了 bool，但沒有排除 float（`1.0` 會被當成 `1`）。
- 欄位的位置資訊是 `None` 時，評分程式會當掉，而不是判 FAIL。
- 覆蓋文件那一項的判斷是「同一行出現兩個關鍵字就 FAIL」，有一種正確的改法會被誤判。六次都沒有用到這種改法。
- 「請求對象不是 interface」只檢查既有診斷還在，兩種合理行為都接受。六次都選擇維持起點行為，參考實作反而選另一種。
- 範圍報告（越界、改 fixture）不計入 13 項，需要人工判讀。我逐份看過，六次都沒有越界。
- 上一題評分程式的三個問題這次都沒有重現：description 比對過嚴、不接受額外的鍵、範圍檢查不用各組自己的起點。

### N-7　不穩定測試規則與起點的既有失敗

- 有一次 run 的 13/13 靠「不穩定測試重跑兩次」這條規則。那個測試是 localhost 連線測試，和改動的模組無關；agent 自己的執行中也遇過；評分是兩次 run 平行跑，會增加連線碰撞。判為環境因素是合理的。
- 這條規則的風險：新測試污染狀態造成的「整套跑才失敗」會被當成不穩定。這次沒有這種跡象。
- 評分環境中，起點有一組 GUI 版面測試失敗，所以這些測試不在回歸偵測範圍內。同一天稍早做參考實作驗證時，起點的測試全部通過，表示評分時的環境與驗證時不同。六次都沒有改 GUI 相關程式。

### N-8　封存

- manifest 只涵蓋四個封存檔，不含評分用到的起點樹與參考實作。
- 封存值沒有由 Owner 在執行前另外保存（結果 §2 已揭露）。§2 第 3 項的三個獨立痕跡補強了時間順序，但仍不是事前的獨立保存。

### N-9　任務契約與規格原文的小出入

- 契約對一個欄位的命名，和規格原文的命名不同。
- 規格原文對同一個欄位的說明前後不一致，契約採用了其中一種解讀。
- 三組收到相同的契約，不影響公平；但「依公開規格」的說法應註明這一處是出題者的解讀。

### N-10　其他

- 六次都被提供雲端連接器的工具命名空間（雖然 MCP 已關閉），實際只用了指令執行與等待兩種工具，沒有用連接器，也沒有用協作工具。
- 有一次 run 檢查了 repo 以上幾層目錄有沒有 `AGENTS.md`（都不存在）。無害，但說明沙箱不擋 repo 以外的讀取。
- 設計 §3.2 要求記錄 `codex.exe` 的 SHA-256，紀錄只有版本與路徑；六次 rollout 的 CLI 版本相同。
- 結果 §4.1「C 組新增的測試數最少」：這是參數化後的案例數。§2 第 20 項顯示六次的測試強度相同，所以「多出的成本沒有換到更多測試」成立，但也沒有證據顯示 C 的測試比較弱。

## 4. 補充限制：三組都用最強的模型設定

- 三組用同一個模型與 effort，是公平比較的必要條件，這一點正確。
- 但用最強的設定會放大天花板：模型幾乎不犯錯，治理沒有東西可以救，只剩成本。
- 結果 §5 寫了「不能推論到較難的任務」，建議再補一句：**也不能推論到較弱的模型或較低的 effort**。
- 單回合 `codex exec` 也碰不到治理的主要用途：跨 session 交接、memory 延續、結案。這比模型強弱更限制結論的適用範圍。
- 如果做下一批，一次只改一個條件：同模型換較難的題目，或同題目三組一起降 effort。不要同時改題目和模型。
