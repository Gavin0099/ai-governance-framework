# 治理效益與 Gate 3 證據對帳

**分析草稿。不是 Gate 3 通過宣稱，不具治理權威，也不授權任何執行、修改、實驗、合併或發布。**

日期：2026-11-15。本文件對照 #273 的自主交付與治理效益問題、#303–#306 的探索性結果，以及一個 Internal Consumer 的真實跨 session 工作。只分析既存紀錄；完整逐行證據與精確成本留於私人報告。公開版不含產品內容、受限位置、內部版本或模型識別，也不轉載真實 session 的精確時間與 token 數。

## 判斷

這個案例補上了短任務試跑沒有驗到的兩件事：新 session 能從既有紀錄接續工作，以及正式結案能沿原生 hook 完成並釋放共享文字持有權。這是單一環境的實際運作證據。

**尚無證據證明完整治理比產品專用流程更容易交付、減少人工救援，或收益大於成本。** 相鄰的產品專用工作也成功跨 session 接續並交付，而且仍使用 PLAN、記憶與 repo 驗證器，不能當作無治理的乾淨對照。

這次找到的可歸因改善很窄：consumer 的既存治理驗證器抓到新增模組未登錄，修正登錄後才通過。這證明該檢查確實補上一個登錄遺漏，不能推論它阻止了產品缺陷，或完整治理相對精簡流程產生額外淨收益。

## 六場工作能支持的結論

下表省略私有任務內容；字母是本案例的 session 代號，並非實驗分組。

| Session | 既存紀錄支持的工作結果 | 接續界線 |
|---|---|---|
| A | 完成自然實作檢查點、驗證及可信交接 | 第一場；prompt 已提供範圍、授權來源與操作指引 |
| B | 只收到最小接續提示，自行讀回紀錄、核對狀態並完成剩餘本機驗收 | 未觀察到 owner 重述或修補交接狀態；仍有協調者安排啟動及後續交付 |
| C | 依審查完成兩項修正 | 收到詳細缺陷與驗收要求；後續又發現回歸 |
| D | 修正前場引入的回歸 | 收到具體派工；尚有後續漏失 |
| E | 實作 owner 新作出的政策裁定 | 有實質需求澄清，不能稱 owner 完全沒有介入 |
| F | 修正後續審查找到的缺陷並交接 | 收到具體派工；Git 與最終交付仍由協調者完成 |

原始紀錄共有六個 session、十三次 CLI 回合。六個一般工作回合沒有提前結案；各場另收到結案請求後才準備候選。六場都留下原生 hook 完成訊號，hook 後快照依序記錄六代有效結案與持有權釋放。

準備完成、hook 完成、有效結案與持有權釋放是不同證據，不能互相替代。一般回合與重複檢查也會顯示 hook 完成，因此不能只看單一成功訊號。

另一次刻意要求舊 session 再結案時，agent 讀到已結案證據便拒絕重建候選。它沒有真的送出 prepare，所以**不是這個真實工作中的機制層拒絕測試**。先前拋棄式環境的機制拒絕，只能留在其原來的證據層級。

既存報告宣稱各場獨立雜湊檢查全過；指定來源留有檢查程式與狀態快照，沒有保存六份完整檢查輸出。本分析沒有重新驗證整套雜湊鏈。快照支持正常狀態轉移，沒有證明併發爭用、錯誤身分或失敗恢復都受到保護。

六場是同一工作的接續與返工，不能當成六個獨立效益樣本。

## #303–#306 的結果需要保留更新順序

依設計既定順序，先判可比較性，再判天花板。全部滿分的產品觀察與無效的比較可以同時成立。

| 資料 | 原始產品觀察 | 最新文件的比較判定 |
|---|---|---|
| #303 設計 | 每組兩次探索性試跑，分開記產品、成本與治理閉環 | 無效先於天花板；不計正式樣本、不直接作機制去留決策 |
| #304 第一批修訂結果 | 六次全為 13/13 | C 對 B 無效；B 對 A 天花板。C2 生效設定退回不同版本，C 組也沒有完整結案 |
| #305 獨立審查 | 重評與更大範圍檢查支持產品正確 | 揭露第一批 C2 的設定差異；舊的兩項皆天花板摘要須配合後來修訂閱讀 |
| #306 第二批結果 | 六次仍全為 13/13 | 兩項比較都無效。B1 設定退回，C 組仍未閉環；另有一項訊息角色差異受限觀察 |

因此不能只說一批遇到 setup 問題。兩批都保留了不可比較條件；滿分不證明組別等效，也不因比較無效而變成產品失敗。

兩批的完整治理組都有較高的原始成本，但有效子集不足、執行順序與服務逾時等因素尚未分離，不能當作可靠的整套治理成本差估計。它們又沒有正式結案，未包含完整收尾成本。

第二批事後的變異檢查顯示，精簡規則與完整治理組的自寫測試都抓到所設變異，基線組漏掉部分。這是探索訊號；檢查事後設計、施加於不同實作，且精簡規則組已全部抓到，不能據此主張完整治理較好。

## 新案例新增的證據及其限制

| 新增的觀察 | 仍缺少的證據 |
|---|---|
| 真實工作中的最小提示接續 | 記憶相對精簡交接省下多少重推導、重做或 owner 修補 |
| 原生 hook、身分與六代結案的正常時序 | 自然出現的身分錯用、重複操作、併發衝突或失敗恢復攔截 |
| 收尾回合、證據量與整合摩擦可見 | 完整金額、人工工時、混合回合中的治理成本及反事實淨收益 |
| 有本機驗證、審查及修復紀錄 | 事前密封獨立產品 oracle、完整介入帳與正式結果採納 |
| 一次真實登錄遺漏被驗證器抓到 | 這項檢查相對既有產品流程的額外收益及可轉移性 |

既有報告開頭停在較早的交付狀態，後面才追加後續 session 與交付結果；本分析以相應原始紀錄對帳。遠端交付細節只有保留的報告陳述，本次沒有查詢遠端。

本案例也沒有完整載入所有常駐治理指令的證據：各回合都有指令預算截斷警告。hooks 實際運作與「全部文字規則都已載入」必須分開。

## 已量得的成本（四捨五入）

下表取自私人報告第 4 節；時間、比例與次數只盤點既存紀錄，不是同任務對照或淨效益估計。

| 項目 | 約數 | 解讀限制 |
|---|---|---|
| 六次正式結案回合 | 約 20 分鐘，占約 94 分鐘 CLI 實測時間的 21% | 包含讀檔、準備與核對，不只是 hook 執行時間 |
| 正式結案 token 增量 | 約占六場結案後顯示值合計的 12% | **僅在顯示值為同 session 累計時成立**；分子與分母均不含刻意重複結案檢查，不是總 input 或帳單金額 |
| 刻意重複結案檢查 | 約 2 分鐘 | 驗證本身的額外成本，不能算成避免事故的收益 |
| 指令預算截斷警告 | 13/13 個 CLI 回合都有 | hooks 運作不等於全部治理文字均已載入 |
| 回合間的混合區間 | 約 1 小時 42 分；總經過時間約 3 小時 16 分 | 含協調、驗證、review、等待及空檔，不等於協調者實際工時，也不能全歸因於治理 |

工作回合中的產品與治理成本仍未分攤；精確 token 組成、金額及人工工時未量得。不能直接相加 resumed 回合的累計顯示值；若累計假設不成立，上述 token 比例即不可使用。這些數字不補足完整維護成本或治理淨收益的證據。

## 收益宣稱的唯一分類

分類對象是收益命題。技術行為已經發生，不代表它降低錯誤、人工或成本的收益已經證明。每列只歸一類。

| 命題 | 唯一分類 | 判斷 |
|---|---|---|
| 發現並補上新增模組的登錄遺漏 | **attributable improvement** | 有實際拒絕、補登及通過的連續原始紀錄；效用限於 consumer 的既存登錄檢查 |
| 正式結案及額外重複檢查 | **governance overhead** | 有額外回合、耗時、工具操作與用量；精確值留私人報告 |
| 治理讀檔、寫記憶、用法除錯及壓力處理 | **governance overhead** | 出現 API 誤用、讀回不符及重試；混合回合未精確分攤，不能填零 |
| 協調、信任、封存舊狀態及整合維護 | **governance overhead** | 有必要 setup、可避免重試及額外派工；部分屬既有產品流程，人工增量未量得 |
| 證據保留及超出載入預算的指令 | **governance overhead** | 體積與操作可計數；更多檔案不等於更多產品收益 |
| 完整治理提高產品成功或減少缺陷 | **unproven capability** | 相鄰產品專用工作也成功；沒有同任務對照，期間仍有漏失與回歸 |
| 記憶降低重推導、重做或 owner 救援 | **unproven capability** | 最小提示接續已觀察；節省量與相對效果未證明 |
| 已授權目標能無人值守持續交付 | **unproven capability** | 啟動、結案、派工及 Git 交付仍依賴協調者 |
| R2 已防止真實重複結案、錯用身分或並行覆蓋 | **unproven capability** | 正常路徑成功；重複請求只由 agent 自制，機制拒絕仍只有拋棄式觀察 |
| 一般回合不結案已避免實際損失 | **unproven capability** | 正確行為已觀察，沒有本案例會誤結案的實際事件或同條件對照 |
| receipts 在自然接續中改變行動並省下修復 | **unproven capability** | 有刻意重複請求的有限反應，尚無自然事件的完整行動改變與結果鏈 |
| canonical memory 保證內容及授權正確 | **unproven capability** | 本次讀回可用，但仍有紀錄膨脹、重試及過去編碼錯誤；寫入不是語意保證 |
| 完整治理比精簡規則建立更強測試 | **unproven capability** | 事後變異檢查沒有完整治理優於精簡規則的訊號 |
| 治理防止未授權交付或錯誤完成宣稱 | **unproven capability** | 沙箱、prompt、原生工具審批及 framework 的作用尚未隔離 |
| 稽核鏈已降低人工核對時間或誤判 | **unproven capability** | 可查性存在，實際節省及比較未量得 |
| 可跨日、跨 repo、跨使用者延續 | **unproven capability** | 單一 consumer、同一天與同協調流程 |
| 「完整治理」代表全部指令均有效載入 | **unproven capability** | 實際有截斷警告；成功 hooks 不能證明全部規則生效 |
| 淨收益足以作正式機制去留決策 | **unproven capability** | 無適用的已凍結成本門檻及可信淨效益估計 |
| 可宣告正式產品自主驗收、Gate 3 或成熟度達標 | **unproven capability** | 驗收、計數資格、結果採納及一般化證據均不足 |

沒有觀察到額外收益，不等於證明治理沒有價值；也不能以安全收益難量測為由，將每個正常結果都列為效益。必要安全邊界不因短題無差異而移除。

## Gate 3 的界線保持不變

#273 已明確分開真實跨 session 驗收、三臂治理效益研究，以及四臂 Engineering Skill 研究的 Gate 3／4。這三條證據不能互相替代；Gate 3 也不等於框架成熟度 G3 或 G4。

既有 Skill 研究要求共同基礎、事前凍結處置及 oracle、盲評與對應產出版本的證據；Gate 3 至少需要跨兩個 consumer、三個不同來源與根因的自然 bug 工作。本案例不具備該研究的處置、對照、計數與版本綁定。工作階段的有效結案也不能替代 command-level 產品驗證資格。

六場正常運作不補足既有 Gate 2 過程完整性、獨立外部權威或歷史無效結果；不重新採納舊樣本，不改 Gate 3 狀態，不授權下一次 counted run。機制去留與安全規則變更仍需各自的既有決策程序。

## 最小下一筆觀察

優先觀察的問題是：**治理保存的狀態，是否在真實交接中改變下一個 session 的行動，避免錯誤重做、越界或 owner 重述。**

只在下一次原本就要發生、另有適當授權的自然交接中，碰到舊摘要或提示與既有正確證據不一致時，利用原有紀錄保留：

1. 原本候選的下一步、真實狀態及既有授權界線。
2. session 自行讀取哪筆證據，因哪個事實改變下一步，保留動作前的原始行。
3. 協調者用既有產品／版本證據核對新行動正確，並記有無 owner 補述、救援及查核成本。

不刻意污染記憶，不製造缺陷，不執行危險操作；沒有自然事件就維持未證明。只看到讀檔、普通接續或又一次成功結案仍不算這個命題的證據。

一筆符合條件的事件能支持一件證據介導的行動修正，不能證明平均因果效益、成本效益或 Gate 3。此處只是觀察建議，沒有開新實驗，也不授權 consumer 修改。

## 新增定性觀察（2026-11-16）：多 Repo 首次導入的治理成本與範圍擴張

**來源及界線：** Owner 提供的一次匿名 Internal Consumer 多 Repo 導入／排障回報，涉及三個各自維護 Submodule、指令、Hooks 與 Git 狀態的工作區；回報時兩個 Repo 已完成靜態接線與部分原生 Runtime 驗證，第三個尚未正式導入。以下是**定性案例，不是 #273 的 E-01 計數樣本**；未獨立核對完整本機收據、分項耗時、模型用量或可比較的對照組，亦不回填上方六個 Session 的數據或收益分類。

| 已回報的現象 | 可支持的結論及限制 |
|---|---|
| 三個 Repo 各有版本、Hook、指令及工作區狀態 | 初次導入工作量隨獨立 Consumer 增加；尚無數據證明 Repo 數量是主要耗時因素 |
| 同一輪需排查 Harness 信任、Session 身分來源、Closeout、首次導入控制檔 | 接線與環境問題造成額外排障；有些驗證只在隔離環境成立，不代表已完成每個正式工作區的原生驗收 |
| L2 獨立 Reviewer 觸發被反覆演練 | 回報顯示可主動啟動 Reviewer，且缺少必要測試時沒有宣稱安全通過；Reviewer 仍可能漏掉關鍵失敗模式，所以「有啟動」與「審查品質合格」必須分開 |
| 治理導入途中另外發現 Consumer 產品／安全性疑慮 | 有值得獨立追查的風險，但尚未證明必須全部納入同一輪治理導入的 DONE；不應把產品疑慮直接轉化為 Framework 新機制 |

**判讀：** 本案支持「治理驗證的邊界曾擴張，會帶來額外工作與維護摩擦」這項觀察，**不支持**「多 Repo 不是主因」、「重複 L2 測試是最大成本來源」、或「完整治理淨效益為負」等定量因果結論。必要的首次驗證、可重用的重複驗證，以及意外發現的安全調查，必須分開計算，不能一律視為浪費。

**Owner 的後續工作方向**已納入 [#273](https://github.com/Gavin0099/ai-governance-framework/pull/273)：一般更新採受影響 Surface 的最小驗證，核心機制／新 Harness 接線採有界完整驗證；原任務 DONE 後停止，非阻擋的新發現另行追蹤；沿用已驗證流程，避免每個 Repo 重做同一證明。這是**既有計畫的決策紀錄**，未授權新 Gate、全域 Profile、Hook、自動化或新的成本實驗；不放寬安全／Owner Gate。

**下一次自然工作可觀察的成本資料：** 哪些檢查是首驗必要、哪些被重複執行、哪些是產品安全另案、實際花費的時間／Token／人工救援，以及有哪些被證據支持的風險攔截。沒有可取得的數據就保持 UNKNOWN；不為量測另造任務。
